# Translating Polaris

Polaris is written in US English (`en-US`) and Spanish of Spain (`es-ES`). Every
account has a language; it is detected when the account is made, changed under
Account > Preferences, and applied at once in every tab the account has open.
URLs never carry the language.

This is the guide for moving a screen onto the catalogs. The account preferences
screen, the rail, the app switcher and the account menu are done and are the
reference: read them next to this.

## How it fits together

| Piece | Where | What it does |
| --- | --- | --- |
| Locale registry | `packages/core/src/i18n/locales.ts` | The locales, their names, the languages and countries each answers for, the formats each implies. |
| Detection | `packages/core/src/i18n/detect.ts` | `Accept-Language` with q-values, `navigator.languages`, the country of the address. Pure. |
| Engine | `packages/core/src/i18n/messages.ts`, `catalogs.ts` | ICU MessageFormat via `intl-messageformat`; typed keys; `defineCatalogs`. Pure, used by the dashboard and by installed apps. |
| Catalogs | `apps/web/messages/<locale>/<namespace>.json` | The dashboard's words. `en-US` is the source; its keys are the types. |
| Request locale | `apps/web/src/lib/i18n/request.ts` | `getLocale()`, `getTranslations(ns)`, detection on the first request. |
| Account locale | `apps/web/src/lib/i18n/locale-service.ts` | `getUserLocale(userId)`, cached, invalidated by `setUserLocale`. |
| Any locale, no request | `apps/web/src/lib/i18n/translate.ts` | `translate(locale, "ns.key", params)`, pure. |
| Browser | `apps/web/src/components/i18n/` | `useTranslations(ns)`, `useLocale()`, `<Messages>`, live switching. |

### Why `intl-messageformat` and not next-intl

Both format ICU messages with the same parser: next-intl uses `intl-messageformat`
underneath. What next-intl adds on top is what Polaris cannot use:

- **Its request config is a Next plugin alias.** Installed apps are loaded into the
  process as bundles and never pass through Next's compiler, so an app's server
  code could not reach `getTranslations`. The language also has to be known in a
  job with no request at all - a line sent into a game for a linked player.
- **Its locale comes from a route segment or middleware.** Here it comes from the
  account, so the pieces it would replace are the ones Polaris writes anyway.
- **Its footprint.** 4.x depends on `@swc/core`, `@parcel/watcher` and an
  extractor plugin (native binaries per platform) for a feature set this uses a
  fraction of. `intl-messageformat` is two small packages from the same
  maintainers.

So the engine is `intl-messageformat` (plural, select, number, tags, the CLDR
plural rules the browser uses) and the rest is a thin layer here: namespaced
catalogs, keys typed from the `en-US` JSON, a server API, a client provider, and
one translator that works the same in a server component, a client component, a
bundle and a job.

## Catalogs

```
apps/web/messages/
  index.ts              every locale, one line each
  en-US/index.ts        one import per namespace
  en-US/common.json     generic words: Save, Cancel...
  en-US/nav.json        the frame: rail, switcher, account menu
  en-US/account.json    the account screens
  es-ES/...             the same files, the same keys
```

- **One namespace per area**, named after the area: `account`, `chat`, `drive`,
  `deploy`, `admin`, `tasks`, `mail`, `notes`, `office`, `vault`, `watch`...
  `common` is for words that mean the same on every screen and nothing else -
  do not grow it into a dumping ground. `node scripts/i18n-scan.mjs` names the
  areas.
- **A new namespace** is a JSON file in every locale folder and an import line in
  each locale's `index.ts`. The catalog test fails when the two disagree.
- **A new locale** is its folder (copy `en-US`, translate every value), one entry
  in `LOCALES` / `LOCALE_INFO` in `locales.ts`, and one line in
  `apps/web/messages/index.ts`. `defineCatalogs` does not compile until every
  registered locale has its catalogs.
- **Keys** are camelCase, grouped by what they belong to on the screen, never by
  where the words happen to sit: `display.theme.label`, `language.hint`,
  `account.status.placeholder`. Name what the message is for, not what it says:
  `language.unsupported`, not `thatLanguageIsNotAvailable`.
- **Values** are ICU MessageFormat. `{name}` fills in; `{count, plural, one {#
  file} other {# files}}` counts; `{kind, select, file {...} other {...}}`
  chooses; `<link>text</link>` marks a part the component draws. An apostrophe
  is literal unless it is next to a brace.

`test/i18n/catalogs.test.ts` fails when a locale misses a key the source has (or
has one it does not), when a message is not valid ICU, and when a translation
uses different arguments or tags than the source.

## Translating a screen

### Server components

```tsx
import { getTranslations } from "@/lib/i18n/request";

const t = await getTranslations("account");
return <h1>{t("preferences.title")}</h1>;
```

### Client components

The namespace has to be handed down. `common` always is (the root layout), `nav`
is inside the app frame; anything else is wrapped where the page is drawn:

```tsx
// page.tsx (server)
import { Messages } from "@/components/i18n/messages";

return (
    <Messages namespaces={["account"]}>
        <PreferencesForm />
    </Messages>
);
```

```tsx
// preferences-form.tsx ("use client")
import { useTranslations } from "@/components/i18n/i18n-provider";

const t = useTranslations("account");
const tc = useTranslations("common");
<Button>{busy ? tc("actions.saving") : tc("actions.save")}</Button>;
```

Only the namespaces a page asks for reach the browser. Never import
`messages/index.ts`, `lib/i18n/translate.ts` or `lib/i18n/request.ts` from a
client component - the catalog test fails if you do.

A list of options, fields or columns declared at module level must become a
function of `t` (see `buildFields` in `display-preferences-form.tsx`): a
module-level constant is frozen in whichever language loaded it first.

### Server actions and route handlers

An action's reply is read by the person who pressed the button, so it is
translated in their language before it is returned:

```ts
const t = await getTranslations("account");
if (!parsed.success) return { error: t("errors.unsupportedChoice") };
```

A route handler does the same. `getLocale()` inside an action is the reader's:
the real session's, even while an administrator is viewing as somebody else.

### Zod messages

Schemas shared between client and server live in `@polaris/core` and have no
reader to ask. Until an area is migrated their messages stay English. When you
migrate one, move the words out of the schema: give the refinement a key as its
message (`"errors.nameRequired"`) and translate the issue where it is shown -
`t(issue.message as NamespaceKey<"account">)` in the form, the same in the
action. Keep those keys in the namespace of the area that owns the schema.

### Toasts and confirmations

Same as any other text: the component that raises it translates it.
`toast.show({ title: t("switcher.saveFailed") })`.

### Dates, numbers, relative times

- Dates and times go through `useDisplayFormat()` / `getDisplayFormat()` as
  before. The reader's language now decides the formats nobody chose (a Spanish
  reader on an instance with no house style gets day-first dates and a Monday
  week), and `format.number()` / `format.currency()` punctuate in it.
- Format a date **before** it goes into a message and pass it as text:
  `t("account.until", { time: format.time(at) })`. ICU's own `{at, date}` would
  ignore the account's time zone and chosen order.
- `<RelativeTime>` phrases itself in the reader's language.
- Day names: `weekdayNames(locale, "long" | "short")` from `@polaris/core`, not
  `WEEKDAY_NAMES` (English only).

### Plurals and names

- Every count goes through `plural`: `{count, plural, one {# file} other {#
  files}}`. Spanish and English happen to share `one`/`other`; the next language
  may not, and the catalog will say so.
- A person's name, a file name or anything else a user typed is a parameter,
  never part of a key and never translated: `t("greeting", { name })`.

### Never glue translations together

`t("a") + " " + t("b")`, or a sentence split around a link, fixes the English
word order into every language. One sentence is one message; the part that is a
link or a button is a tag in it, drawn with `t.rich`:

```tsx
{t.rich("accessibility.defaultIs", {
    size: standard,
    back: (chunks) => <button key="back" onClick={reset}>{chunks}</button>
})}
```

```json
"defaultIs": "The default here is {size}px. <back>Go back to it</back>"
```

Every tag's value must be a function of its `chunks` (`(chunks) => <button>{chunks}</button>`
above), never an element handed over directly (`time: <RelativeTime iso={at} />`).
`t.rich` throws on a tag given anything else, the translator answers with the
raw message, and `Last active <time></time>` reaches the reader with the
markup printed as text - nothing at build time says so, and plain `t()` on a
tagged message fails the same way. `test/i18n/tagged-messages.test.ts` scans
every call site in every app for both mistakes; see
`docs/bugs/sessions-last-active-printed-time-markup-instead-of-time.md` for
where this was first seen.

### Length: a translation takes the room of the English

Buttons, tabs, menu items, column headers, badges and field labels are sized by
their words. A Spanish label a third longer than the English one wraps onto a
second line, overflows its box or stretches the row that fit in English, so a
translation is written to the English length, not just to its meaning:

- Pick the shorter natural wording: `Guardar`, not `Guardar cambios`, for
  `Save`; `Ajustes`, not `Configuración`; `Cambios/semana`, not `Cambios a la
  semana`. Drop articles and "de la" chains a label does not need.
- Never shorten into an abbreviation nobody uses or a word that changes the
  meaning. When no natural wording fits, the layout gets the room instead
  (`min-w-0` + `truncate` with the full text in `title`, or a wrap that was
  designed for), and the change says so.
- Prose that wraps - hints, descriptions, errors written as sentences - is
  exempt; it should still not grow for its own sake.

`test/i18n/lengths.test.ts` holds it: a label (at most 32 characters of English,
no argument, no tag, not ending in `.`, `!`, `?` or `:`) may be longer than the
English by 3 characters or a quarter, whichever is more. `scripts/i18n-long.json`
lists the labels that were over when the rule came in; it only shrinks. A new
label over the budget fails the test, and shortening a listed one means removing
its line.

### Labels that are data

The app catalogue (`lib/apps.ts`) is data read by the rail, search and the
Overview, and its labels stay English there. They are translated where they are
drawn, with `useNavLabel()`, from `nav.labels` - keyed by the English. The
navigation catalog test fails when a screen is added without its label. Never
pass a name somebody chose (an organization, an installed app) through it.

Packages that draw but do not know the language (`@polaris/ui`) take their words
as props with English defaults - see `AppSwitcher`'s `strings`.

## Code with no screen: `getUserLocale` and `translate`

Notifications, emails, a job, a message sent into a game: find out whose
language, then translate with no request around it.

```ts
import { getUserLocale } from "@/lib/i18n/locale-service";
import { translate } from "@/lib/i18n/translate";

const locale = await getUserLocale(userId); // cached, never null
const title = translate(locale, "nav.account.signOut");
```

`getUserLocale` is cached in memory for a few minutes and updated the moment the
account changes its language.

## Installed apps (bundles)

An app cannot import the dashboard, and ships its own catalogs:

```
apps/game-servers/messages/en-US/index.ts   export default { games }
apps/game-servers/messages/en-US/games.json
apps/game-servers/messages/es-ES/...
apps/game-servers/messages/index.ts
```

```ts
// apps/game-servers/messages/index.ts
import enUS from "./en-US";
import esES from "./es-ES";
import { defineCatalogs } from "@polaris/core";

export const gameCatalogs = defineCatalogs({ "en-US": enUS, "es-ES": esES });
```

On the server, the language comes from the host contract:

```ts
import { host } from "@polaris/app-host";

const t = gameCatalogs.translator(await host.i18nRequest.getLocale(), "games");
const forPlayer = gameCatalogs.translator(await host.i18nLocaleService.getUserLocale(userId), "games");
```

In the browser:

```tsx
import { hostUi } from "@polaris/app-host/client";

const t = gameCatalogs.translator(hostUi.i18nProvider.useLocale(), "games");
```

The catalog test finds `apps/*/messages` on its own and holds an app's catalogs
to the same rules as the dashboard's.

## How the language is chosen

At account creation (setup, invite) and on the first request of an account that
has none, in this order:

1. The `polaris-locale` cookie - the language this browser was reading Polaris in
   (the sign-in screen writes it from `navigator.languages`).
2. `Accept-Language`, by q-value. `es`, `es-MX`, `ca-ES`, `gl`, `eu` read Spanish;
   `en-GB` reads US English.
3. The country of the address (`geo-service`, cached, 1.5 s at most): a
   Spanish-speaking country reads Spanish.
4. `en-US`.

A country lookup that times out is not written down, so the next request tries
again. Signed-out pages use the cookie, then `Accept-Language`, and never the
country.

## Switching live

`setLocaleAction` stores the choice, sets the cookie and publishes it on the
account's live stream (`/api/access/stream`, the one the access watcher uses).
`LocaleWatcher` in every other tab sets `<html lang>` and the cookie and calls
`router.refresh()`; the server draws the page again in the new language and the
providers receive it. The tab that made the change is redrawn by the action's
revalidation.

## Measuring progress

```sh
cd apps/web
npm run i18n:scan              # strings left, per area
npm run i18n:scan -- --list chat
npm run i18n:scan -- --json
```

A heuristic: text between JSX tags, copy props (`title`, `placeholder`,
`aria-label`, `label`, `alt`...), and the same names as object properties
(option lists, toasts, `{ error: "..." }`). Mark a literal that is not copy with
`// i18n-ignore`.

## Checklist for one area

1. `npm run i18n:scan -- --list <area>` for the inventory.
2. Create `<namespace>.json` in `en-US` with the current English, word for word -
   an English reader must see no change - and add it to `en-US/index.ts`.
3. Replace each literal with `t(...)`: server components `getTranslations`,
   client components `useTranslations` under a `<Messages>`, actions translate
   their replies. Lists at module level become functions of `t`.
4. Sentences with a link or a button become one message with a tag; counts
   become `plural`; dates are formatted first and passed in.
5. Write `es-ES/<namespace>.json`: Spanish of Spain, natural and short - `tú`,
   not `usted`; `Guardar`, not `Salvar` - and each label about as long as its
   English (see "Length"). Add it to `es-ES/index.ts`.
6. Update the tests that render those components (`withMessages` in
   `test/setup/i18n.tsx`).
7. Add every fully migrated file to `scripts/i18n-migrated.json`.
8. `npx tsc --noEmit -p .` and `npx vitest run test/i18n` - and read the screen
   once in each language, looking for a button, tab or header that wraps or
   grows in Spanish.
