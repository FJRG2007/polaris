# Upstream sync

Polaris Terminal is a fork of [warpdotdev/Warp](https://github.com/warpdotdev/warp). This file records how far it has been brought forward, so `/catch-up` knows where to start.

**Last synced upstream commit:** `f8223cef2d167a5858bf233df8a1fb6f74537fa5` (2026-11-20, "Bump Rust 1.94 and Candle 0.11.1 to drop zip 7.2.0 (#16946)")

## Where Polaris Terminal deliberately differs

Taking an upstream change on top of one of these would silently undo it. Check before porting anything that touches them.

| Area | Polaris Terminal's position | Where |
| --- | --- | --- |
| GPU selection on Windows | Defaults to the discrete GPU. Upstream prefers the integrated one, which renders the terminal on the iGPU of any machine with a dedicated card. Crash recovery falls back to integrated rather than out of it. | `app/src/settings/gpu.rs`, `app/src/crash_recovery.rs` |
| `blocks` table | Indexed on `(pane_leaf_uuid, is_background)`, and blocks belonging to closed panes are deleted at startup. Upstream has no index and no cleanup, so the retention count after every command scans the whole table. | `crates/persistence/migrations/2026-09-07-120000_index_blocks_and_command_history`, `app/src/persistence/block_list.rs` |
| Repository watcher on Windows | `Repository::check_gitignore_status` stats a path only when a directory-only pattern makes its kind matter. Upstream stats every path in every filesystem event on the main thread, so a build or a worktree filling an open repository stalls the window for minutes. The gitignore set also includes `<repo>/.git/info/exclude`, anchored at the working tree (and read from the shared git directory for a linked worktree), which upstream never loads at all - so everything an agent excludes there, its own worktrees above all, counts as tracked and reaches the main thread, every subscriber, the file tree and the file search. See `docs/bugs/main-thread-stalls-on-file-floods.md` and `docs/bugs/git-info-exclude-is-never-loaded.md`. | `crates/repo_metadata/src/repository.rs`, `crates/repo_metadata/src/entry.rs`, `crates/repo_metadata/src/gitignore_cache.rs` |
| Session persistence | Written every 15 seconds and again on termination. Upstream only writes on window move, resize, focus change and close, so a shutdown loses whatever changed since the last of those. Upstream closes each tab as Windows kills its shell, so a restart brings back one. Finding an update is also not an error here: upstream's `UnableToUpdateToNewVersion` means "you are not allowed to install this" and is drawn in red, while on this fork it is the ordinary outcome, so the banner and the two menu entries say a version is available and offer to open the release page. Other consumers of that field do not - `fetch_channel_versions_from_json_storage` interpolates it into a relative path - so it is not safe to read the empty string as "any consumer will cope". The "more info" link behind the failure went to `docs.rook.dev`, which the rename invented and somebody else owns. | `app/src/autoupdate/github.rs`, `app/src/autoupdate/mod.rs`, `app/src/workspace/view.rs`, `app/src/bin/oss.rs`, `app/src/resource_center/main_page.rs`, `crates/pterm_core/src/context_flag.rs` |

This is upstream's own scheme, which the tree was already built for and this fork spent three releases not using: `ParsedVersion` parses nothing else and `script/update_plist` derives the numeric `CFBundleVersion` from those fields. A date also says more than a semver number would, there being no published API here to promise compatibility about. | `script/release_tag`, `CLAUDE.md` |

## What the rename must not touch

`script/rebrand.py` carries the current list and the reasoning. In short: repositories under the upstream organisation other than the client itself, the five external crates whose package names carry the upstream brand, and the protobuf types and fields reached through `api::`. Each of those lives in another repository, so renaming it here only breaks the build.

There is one exception of a different kind: `warp pointer`, in `crates/computer_use/src/linux/x11/`. That is the English word - X11's `XWarpPointer` teleports the cursor and predates the terminal by decades - so the name is local code, not a foreign identifier, and it is a collision the "belongs to another repository" rule would never flag. Renaming it broke the Linux build, which nothing checked from Windows.

Those are names the rename must leave alone. There is a second failure mode it cannot prevent, because nothing in the renamed text is wrong: **assertions that depend on a literal it did change.** Four tests broke this way, and all four compiled cleanly.

- `regex_right`, `regex_left` and `nested_regex` search for `Wa.*123` and `Wa.*rp` in fixtures that said `Warp`. The needles are fragments, not the whole word, so they stayed put while the haystack became `Polaris Terminal` and the searches began returning `None`.
- `test_find_url_omits_trailing_periods` hard-codes the columns a URL occupies. `github.com/warpdotdev/Warp` became `github.com/FJRG2007/polaris` and lost two characters; the column numbers did not move.
- `deserialize_mixed_environment_uses_per_repo_forges` is the inverse: its fixture's `"repo": "warp"` was renamed to `"polaris-terminal"`, while the clone URL it asserts, `https://github.com/warpdotdev/warp.git`, was *deliberately preserved* by the rule that protects the upstream repository. The protection and the rename disagreed, and the test compared one against the other.

After re-running the rename, run the tests on every platform rather than only building. A fragment of the brand used as a search pattern, and a hard-coded length or offset into a renamed literal, are the two shapes to look for.
